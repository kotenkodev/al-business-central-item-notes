# 1.5. Производство: от компонентов к готовому изделию

[К оглавлению](<Business Central and AL.md>) · [Назад](1.4-locations-and-warehouse.md) · [Далее: tracking](1.6-item-tracking.md)

## 1. Что делает производство

Производство преобразует несколько запасов и затраты на работу в другой запас. Для простого опыта возьмём одно изделие TRAIN-FG:

| Компонент | Количество на изделие | Стоимость единицы | Стоимость потребления |
|---|---:|---:|---:|
| TRAIN-C1 | 2 | 10 | 20 |
| TRAIN-C2 | 1 | 30 | 30 |
| TRAIN-C3 | 3 | 15 | 45 |
| Итого | Не складываем разные товары в одну физическую единицу | — | 95 |

После изготовления одного изделия компонентов меньше, готовой продукции больше. Стоимость 95 переносится через незавершённое производство — WIP, Work in Process.

WIP удобно представить как коробку «в работе»: материалы уже использованы, но их стоимость ещё не полностью признана стоимостью готового выпуска.

## 2. Production BOM и Routing

Production BOM — состав изделия: какие компоненты и в каком количестве нужны. Routing — операции: где и как выполняется работа, какие мощности и время используются.

| Понятие | Что описывает |
|---|---|
| Production BOM Header / Lines | Рецептуру и компоненты |
| BOM Version | Версию состава и её применимость |
| Routing Header / Lines | Последовательность операций |
| Work Center / Machine Center | Производственный ресурс |
| Routing Link Code | Связь компонента с операцией |
| Production Order | Конкретное задание на изготовление |

Для использования BOM обычно нужен подходящий статус, например Certified, и корректные даты версии. В Item Card готового изделия настраиваются способ пополнения, Production BOM No. и при необходимости Routing No.

Изменение BOM не должно восприниматься как автоматическое переписывание всех уже созданных заказов. Компоненты и операции заказа — его рабочая копия; Refresh/Replan имеют собственную семантику и требуют проверки. [Create production orders](https://learn.microsoft.com/en-us/dynamics365/business-central/production-how-to-create-production-orders).

## 3. Статусы заказа

| Статус | Назначение |
|---|---|
| Simulated | Моделирование и оценка без обычного оперативного исполнения |
| Planned | Плановое предложение, которое может пересчитываться планированием |
| Firm Planned | Более устойчивое плановое решение |
| Released | Заказ для исполнения и регистрации факта |
| Finished | Завершённый заказ, важный для окончательной обработки стоимости |

Released не означает, что компоненты автоматически уже списаны при любой настройке. Это зависит, в частности, от Flushing Method. Finished не является синонимом «все расходы уже перенесены в General Ledger».

## 4. Consumption

Consumption отражает использование компонентов. Для обычного потребления 2 единиц в Consumption Journal вводят количество 2; Item Ledger Entry типа Consumption уменьшает запас на 2.

Calc. Consumption предлагает строки по ожидаемому или фактическому выпуску в зависимости от параметров. Предложенное число нужно сравнить с реальностью: фактическое потребление может отличаться из-за брака, замены материала или изменения количества выпуска.

Важные поля: Prod. Order No., Prod. Order Line No., Prod. Order Comp. Line No., Item No., Quantity, Location Code, Bin Code и tracking. Неправильная связь с компонентом заказа может дать неверный остаток потребности даже при правильном Item No.

Складской процесс может требовать предварительный pick/movement. Нельзя считать, что Consumption Journal всегда разрешает списать любое наличие Location. [Post consumption](https://learn.microsoft.com/en-us/dynamics365/business-central/production-how-to-post-consumption).

## 5. Output и Capacity

Output отражает выпуск готового изделия. Output Journal также может регистрировать время операций. Capacity Ledger Entry описывает использование мощности, а связанные Value Entries — его стоимость.

При Routing промежуточная операция не обязательно создаёт новый запас готового товара: количественный выпуск связан с соответствующей конечной операцией. Поэтому десять зарегистрированных операций не означают десять готовых изделий.

Нужно различать:

- Output Quantity — выпущенное количество;
- Scrap Quantity — брак в контексте операции;
- Setup Time — подготовительное время;
- Run Time — время работы;
- Remaining Quantity — то, что ещё предполагается выполнить.

Нормы и единицы времени важны не меньше количеств материалов. Ошибка «минуты вместо часов» способна сильно исказить capacity cost. [Post output and run times](https://learn.microsoft.com/en-us/dynamics365/business-central/production-how-to-post-output-quantity).

## 6. Flushing Method

| Режим | Идея |
|---|---|
| Manual | Пользователь явно регистрирует потребление |
| Forward | Автоматическая регистрация на предусмотренном раннем этапе |
| Backward | Автоматическая регистрация при предусмотренном завершении / выпуске |
| Pick + соответствующий режим | Учитывается складской отбор перед автоматическим потреблением |

Точная точка автоматического списания зависит от настройки компонента, Routing Link и процесса. Нельзя одновременно вручную списать всё и без проверки запустить flushing: возможно двойное потребление.

Для первого числового опыта используйте Manual, чтобы каждое изменение было наблюдаемым. Затем повторите на отдельном заказе с автоматическим режимом. [Flushing components](https://learn.microsoft.com/en-us/dynamics365/business-central/production-how-to-flush-components-according-to-operation-output).

## 7. Движение стоимости и WIP

Свёрнутая экономическая схема для примера без работы и overhead:

| Этап | Дебет | Кредит |
|---|---|---|
| Consumption 95 | WIP 95 | Components Inventory 95 |
| Окончательная стоимость Output 95 | Finished Goods Inventory 95 | WIP 95 |

Реальные строки General Ledger зависят от Posting Setup и механизма отражения стоимости. Номера счетов 14140 или 14210 из демонстрации не являются обязательными номерами BC.

До завершения стоимостной обработки выпуск может иметь предварительную стоимость. После Finished и cost adjustment затраты распределяются на выпуск, а для Standard отдельно учитываются variances. Остаток WIP нужно оценивать после соответствующих процессов, а не только после изменения статуса. [Production order posting](https://learn.microsoft.com/en-us/dynamics365/business-central/design-details-production-order-posting).

### Если есть работа и overhead

При материалах 95, работе 20 и дополнительных производственных затратах 5 экономическая стоимость выпуска может стать 120. Нельзя ожидать равенство Output только сумме материалов, если включены другие составляющие.

### Если выпущена только часть

Заказ на 10, фактически выпущено 4. Часть затрат остаётся в WIP или распределяется согласно правилам оценки. «Есть Output» не означает «WIP обязан быть нулевым».

## 8. Исправление потребления и выпуска

Если ошибочно потребили 4 вместо 2, обратное потребление на 2 возвращает материал в запас и уменьшает соответствующие затраты. В ручном Consumption Journal используется отрицательное количество, с корректной связью с исходным движением и заказом.

Сначала проверьте статус заказа, исходную запись, tracking и применённые последующие движения. Отмена Output может быть невозможна, если готовое изделие уже использовано дальше.

В современных версиях есть действие Reverse Production Order Transaction с ограничениями. Microsoft также описывает Reopen для Finished Production Order: однократное повторное открытие и ограничения для заказов без выпуска со списанным WIP. Поэтому правило «Finished никогда нельзя исправить» слишком категорично; доступность проверяют в своей версии. [Reverse and correct production transactions](https://learn.microsoft.com/en-us/dynamics365/business-central/production-cancel-production-orders-that-have-consumption).

Обычное проведение нового Consumption непосредственно в Finished-заказ и поддерживаемый процесс Reopen — разные вещи. Не меняйте Status через таблицу ради обхода проверки.

## 9. Производство, сборка и планирование

Assembly проще подходит для комплектов и сборочных сценариев; его стоимость и жизненный цикл отличаются от Production Order. Manufacturing использует более подробные операции, мощности и WIP.

Planning / MRP рассчитывает предложения пополнения по спросу, запасу и параметрам. Плановое предложение само по себе не является фактом Consumption или Output.

Производственная функциональность зависит от доступного плана/лицензии и Experience. Выбор Premium Experience показывает соответствующую функциональность, но не создаёт лицензионные права сам по себе.

## 10. Практика

1. Подготовьте компоненты с фактурированной стоимостью 10, 30 и 15.
2. Создайте BOM: C1×2, C2×1, C3×3.
3. Создайте Released Production Order на 1 TRAIN-FG, проверьте компоненты.
4. При Manual flushing проведите Consumption 2, 1, 3.
5. Найдите три отрицательных товарных движения и стоимость −95 суммарно.
6. Проведите Output 1.
7. Завершите заказ штатным действием, выполните cost adjustment и при необходимости cost posting.
8. Проверьте итоговую стоимость выпуска 95 и закрытие WIP при оговорённых условиях.

Для отдельного опыта до завершения заказа спишите C1×4 и исправьте лишние 2. Прогноз по C1: −4 +2 = −2.

## 11. Самопроверка

**Почему нельзя сложить количества разных компонентов и сравнить с Output?** Это разные товары и единицы. Сходится денежная стоимость с учётом всех затрат.

**Что означает отрицательный Consumption в журнале?** Обратное движение, возвращающее компонент, если процесс допустим.

**Почему Output уже есть, а стоимость ещё меняется?** Заказ и его источники затрат ещё проходят окончательный расчёт.

**Почему Finished не доказывает нулевой WIP прямо сейчас?** Нужно проверить cost adjustment, General Ledger posting и особенности заказа.
