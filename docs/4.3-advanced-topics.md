# 4.3. Следующие темы и архитектурные границы

[Оглавление](README.md)

## API и интеграции

Начните с готовых API, затем изучайте API Page / API Query. Контракт интеграции должен определять идентичность сущности, Company, версию API, формат ошибок и правила повторов. OData-представление страницы и специально спроектированный API не обязательно имеют одинаковую устойчивость.

SystemId полезен как технический GUID, но внешняя система также может иметь свой ключ. Храните явное соответствие и уникальность: поиск только по изменяемому описанию товара ненадёжен.

Для обновления важно учитывать конкурентность и ETag, для больших выборок — pagination. Для повторяемой команды нужен idempotency key: повтор одной бизнес-команды не должен создавать новый invoice.

Сценарий сбоя: внешний клиент отправил запрос, BC провёл операцию, ответ потерялся. Клиент не знает результата. Правильный повтор должен найти прежний результат по устойчивому ключу, а не снова провести документ.

Официальная отправная точка: [Business Central API overview](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/).

## HttpClient и внешние эффекты

Проверяйте отдельно транспортную ошибку и HTTP status. Успешный transport не означает 2xx. Тайм-аут не доказывает отсутствие действия на удалённой стороне.

Секреты нельзя хранить в репозитории или включать в telemetry. Не держите длинную транзакцию проведения во время нестабильного сетевого запроса. Для устойчивой доставки используйте очередь исходящих сообщений и повторяемый обработчик.

## Job Queue

Фоновое выполнение не имеет обычного интерактивного UI. Процедура должна работать с явными параметрами и собственным контекстом, иметь журнал результата, повторяемость и ограниченный объём транзакции.

Обработчик не должен зависеть от открытой страницы пользователя. Work Date, Company и права фонового исполнения нужно проверять явно. Повтор после ошибки требует понимания, какая часть предыдущей работы уже зафиксирована.

## Reports и Query

Report разделяет получение данных и layout. Неправильный join или вложенные dataitems могут умножить строки и суммы. Сначала докажите правильность dataset, затем оформляйте документ.

Query удобен для структурированного чтения и агрегации. Это не замена posting procedure. Отчёт с правильной суммой за всё время ещё может неправильно учитывать даты, expected cost или валюту.

## Диагностика производительности

Измеряйте продолжительность, SQL statements, блокировки и объём данных. Одна быстрая запись в пустой базе не характеризует работу на миллионе строк.

Частые причины: N+1 чтения, FlowFields внутри больших циклов, отсутствие селективных фильтров, длинные транзакции, внешние вызовы под блокировками. Оптимизация начинается с измерения и воспроизводимого сценария.

## CI и поставка

Сборка должна воспроизводиться вне компьютера автора с известными зависимостями. Pipeline проверяет compile, анализаторы, тесты, установку и upgrade с поддерживаемой baseline. Отчёт должен сохранять версию BC, runtime и пакетов.

Отделяйте учебные эксперименты, тестовые libraries и production package. Настройка publish из VS Code не заменяет процесс управления релизами.

## Что изучать после курса

| Направление | Предпосылка | Учебный результат |
|---|---|---|
| Multicurrency | Понимание General Ledger | Объяснить реализованную и нереализованную курсовую разницу |
| Fixed Assets | Дебет/кредит и периоды | Приобретение, амортизация, выбытие |
| Projects | Затраты и WIP | План/факт проекта и признание результата |
| Planning / MRP | Inventory, BOM, Routing | Объяснить предложение пополнения |
| Service | Документы, ресурсы, tracking | Проследить ремонт и затраты |
| Intercompany | Company и расчёты | Согласовать связанные операции компаний |
| Localization | Налоги и документы | Понять различия обязательных процессов |

Для каждого направления повторяйте общий метод: исходные условия → прогноз → операция → связанные записи → контрольные суммы → ошибочный сценарий. Это позволяет расширять знания без запоминания случайных последовательностей кнопок.
