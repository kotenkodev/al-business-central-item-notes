# 2.5. Автоматические тесты AL

[Оглавление](README.md) · [Жизненный цикл приложения](3.0-appsource-and-lifecycle.md)

## Что проверяет тест

Компилятор проверяет типы и ссылки. Бизнес-тест проверяет наблюдаемое поведение: какие данные появились, что осталось неизменным и какая ошибка возникает при недопустимом вводе.

Arrange создаёт условия, Act выполняет одну операцию, Assert сравнивает результат с независимым ожиданием. Тест, который вычисляет ожидание тем же ошибочным алгоритмом, мало полезен.

## Структура

```al
codeunit 50140 "Training Calculation Tests"
{
    Subtype = Test;

    [Test]
    procedure VipDeliveryIsFree()
    var
        Practice: Codeunit "Syntax Practice";
        Actual: Decimal;
    begin
        Actual := Practice.GetShippingFee(45, true);
        if Actual <> 0 then
            Error('Expected zero; actual %1.', Actual);
    end;
}
```

Этот пример предполагает чистую GetShippingFee без Message. Текущая процедура проекта показывает Message, поэтому до её рефакторинга нужен MessageHandler. Проверяйте свободность ID; пример не предлагается автоматически публиковать поверх существующего объекта.

Сами тестовые методы объявляются [Test], а Codeunit имеет Subtype = Test. Runner организует запуск и сбор результата. Транзакционное поведение задают TransactionModel и TestIsolation; не предполагается, что любой произвольный runner всегда очищает все данные одинаково. [Test methods](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-test-codeunits-and-test-methods).

## Значимые границы

Для ShippingFee нужны случаи 49.99 → 10, 50 → 5, 99.99 → 5, 100 → 0, VIP при малой сумме → 0. Один VIP-тест недостаточен: функция, всегда возвращающая ноль, тоже его пройдёт.

В текущем SyntaxPractice.GetShippingFee вычисляется ShippingFee, но нет exit(ShippingFee). Случай 45 без VIP должен обнаружить различие между сообщением 10 и возвращаемым значением. Formatter не исправляет такую ошибку.

## Проверка ошибок

asserterror ожидает ошибку следующего оператора. После него проверяют текст/код ошибки, чтобы тест не прошёл из-за случайной другой причины.

```al
asserterror Note.Validate("Note Text", '');
if StrPos(GetLastErrorText(), 'Note Text') = 0 then
    Error('Unexpected error: %1', GetLastErrorText());
```

Note здесь — заранее объявленный Record Item Note. Для стабильных тестов учитывайте язык сообщений и не привязывайтесь к случайным системным формулировкам. Отдельно проверяйте, что после неуспеха не появились частичные данные.

## Handlers

MessageHandler принимает сообщение, ConfirmHandler возвращает ответ, PageHandler и ModalPageHandler обслуживают страницы, RequestPageHandler — параметры отчёта.

```al
[MessageHandler]
procedure CheckShippingMessage(MessageText: Text[1024])
begin
    if StrPos(MessageText, 'Shipping fee') = 0 then
        Error('Unexpected message: %1', MessageText);
end;
```

Для использования добавьте [HandlerFunctions('CheckShippingMessage')] к тесту. Объявленный в списке handler должен реально вызываться, иначе тест завершается неуспешно. Не делайте все ConfirmHandler безусловно отвечающими Yes без проверки ожидаемого вопроса: это скрывает лишний UI. [Handlers](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-creating-handler-methods).

## TestPage

TestPage моделирует работу со страницей: открытие, ввод в control, вызов action, чтение результата. Такой тест нужен для связи UI с бизнес-операцией, но не заменяет тест сервиса.

Ввод через TestPage может вызвать validation, которую прямое присваивание Record не вызывает. Выбирайте путь исходя из проверяемого контракта. Если ошибка связана с PageExtension, тест одного Codeunit её не обнаружит.

## Тестовые библиотеки

Library - Sales, Library - Inventory и другие helpers создают согласованные данные. Library Assert предоставляет удобные проверки. Они являются зависимостями тестового приложения, а не магическими встроенными процедурами языка.

В проекте уже объявлены Library Assert и Application Test Library. Проверяйте их установку, symbols и версии. Сигнатуры helper-процедур берите из текущих symbols, не из случайной старой статьи.

## Изоляция и повторный запуск

Тест не должен зависеть от номера покупателя из чужой CRONUS, вчерашней даты, порядка тестов или существующих заметок. Создавайте данные с уникальной идентичностью, фильтруйте проверки по собственному сценарию и используйте управляемые даты.

Commit, SingleInstance-переменные и внешние сервисы требуют отдельной стратегии очистки и изоляции. Rollback базы не очищает состояние внешней системы.

## Матрица для Item Note

| Сценарий | Проверка |
|---|---|
| Корректная заметка | Одна строка с нужным Item No., текстом и Priority |
| Пустой текст | Ожидаемая ошибка, новой строки нет |
| Несуществующий Item | Ошибка соответствующего пути validation |
| RaisePriority | Изменились только заметки выбранного товара |
| FlowField | Считает только связанные заметки |
| Rollback | Count после ошибки равен начальному |
| Ограниченный пользователь | Нужный сценарий работает с рабочими permissions |

## Практика и ответы

Запустите имеющийся ItemNoteTests, прочитайте каждое ожидание, затем добавьте один граничный сценарий, который ловит реальную ошибку. Проверьте повторный запуск в той же учебной компании.

**Почему тест прошёл, а функция неправильная?** Проверенный вход мог совпасть со значением по умолчанию; нужны границы и отрицательные случаи.

**Почему тест завис на вопросе?** Для интерактивного вызова не задан подходящий handler либо тестовый путь вызывает неожиданный UI.

Примеры этого курса не запускались в контейнере; успешное выполнение тестов нужно фиксировать отдельным отчётом runner.
