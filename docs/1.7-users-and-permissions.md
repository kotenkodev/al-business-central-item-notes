# 1.7. Пользователи, лицензии и права

[К оглавлению](<Business Central and AL.md>) · [Назад](1.6-item-tracking.md) · [Далее: среда AL](2.0-al-environment.md)

## 1. Доступ состоит из нескольких проверок

Пользователь должен иметь возможность войти в среду, использовать нужную функциональность по лицензии, открыть объекты и выполнить действия над данными. После этого операция всё ещё может быть запрещена бизнес-правилом.

| Слой | Пример ограничения |
|---|---|
| Identity / authentication | Не удаётся войти |
| Environment access | Пользователь не допущен к среде |
| License / entitlement | Функциональность не входит в доступный план |
| Permission Sets | Нет Read / Insert / Modify / Delete / Execute |
| Company scope / security filters | Доступ ограничен компанией или записями |
| Business rules | Документ Released, период закрыт, отсутствует tracking |
| UI profile | Нужная команда не показана в выбранном рабочем месте |

Последняя строка не является полноценной защитой данных. Скрытая кнопка не запрещает вызов той же операции через другой интерфейс.

## 2. Online и локальная среда

В Business Central Online пользователей и лицензии обычно администрируют через Microsoft 365 / Entra, затем синхронизируют соответствующие данные в BC. Действие Update users from Microsoft 365 обновляет пользователей, но не заменяет проектирование рабочих Permission Sets.

В on-premises пользователями можно управлять непосредственно в BC в соответствии с режимом аутентификации и лицензией сервера. Поэтому утверждение «пользователей никогда не создают в BC» справедливо не для всех развёртываний. Ваш Docker с UserPassword — отдельный случай. [Create users according to licenses](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-how-users-permissions).

## 3. Лицензия и Experience

Лицензия/entitlement ограничивает допустимую функциональность. Permission Set предоставляет права внутри этих границ. SUPER не превращает ограниченную лицензию в другой план.

Essentials и Premium различаются набором бизнес-возможностей; Manufacturing и Service Management требуют соответствующего доступа. Experience влияет на показ функций, но переключение Experience не является покупкой лицензии.

Конкретные актуальные условия лицензирования проверяют по официальной документации и соглашению компании, а не по списку видимых страниц. [Licensing](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/deployment/licensing).

## 4. Permission Set

Permission Set описывает права на объекты и tabledata. В AL обозначения для данных:

| Буква | Действие |
|---|---|
| R | Read |
| I | Insert |
| M | Modify |
| D | Delete |
| X | Execute для исполняемого объекта |

Права на Page и tabledata различаются. Возможность запустить страницу не означает возможность изменять её таблицу. Возможность изменить исходный Sales Header не гарантирует права на все объекты проведения.

Доступ оценивают по эффективному сочетанию назначений, включений и исключений permission sets, entitlement и контексту компании. Упрощение «всегда просто сложить все права» не описывает все современные настройки. [Assign permissions](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-define-granular-permissions).

## 5. Direct и Indirect

Прямое право разрешает действие непосредственно. Косвенное право допускает его через объект с подходящим Permissions property и при остальных выполненных условиях.

Бизнес-смысл: пользователь может проводить Sales Order через стандартную логику, не получая свободу вручную редактировать General Ledger Entry. В AL Permissions property — механизм контролируемого доступа, а не способ произвольно обходить все ограничения.

Заглавные RIMD в permission set обозначают прямые права, строчные rimd — косвенные. Для нового расширения выдавайте права на собственные таблицы и нужные исполняемые объекты; не начинайте с массового доступа ко всем стандартным учётным таблицам.

## 6. Company scope и Security Filters

Permission assignment может быть ограничен Company. Пустой scope и конкретная компания имеют разные последствия; проверяйте фактическое назначение.

Security Filters ограничивают набор записей, доступных через разрешение. Это не обычный пользовательский фильтр списка, который можно просто снять. Код, который игнорирует бизнес-фильтр с помощью Get, не получает тем самым право обходить security model.

Фильтрация справочника и связанных документов требует продуманной модели: пользователь может видеть документ, но не иметь доступа к требуемому связанному значению. Такие ошибки часто выглядят как отсутствие записи.

## 7. Security Groups

Группа позволяет назначить права набору пользователей и управлять членством централизованно. Online использует соответствующую связь с Entra security groups; on-premises имеет свои поддерживаемые варианты.

Не смешивайте security group, ограничивающую доступ к целой среде в admin center, и группу, через которую назначают Permission Sets внутри BC. Это разные точки контроля.

В старых материалах встречаются User Groups. При работе с текущими версиями сверяйте процесс миграции и доступные страницы, а не буквально повторяйте старую инструкцию. [Security groups](https://learn.microsoft.com/en-us/dynamics365/business-central/ui-security-groups).

## 8. Profile / Role

Profile задаёт рабочее место и настройки интерфейса. Роль Sales Order Processor помогает продавцу видеть нужные задачи, но не является автоматическим набором прав на продажу.

Проверка: назначить пользователю другой Role и убедиться, что реальные permissions не изменились. Обратная ситуация тоже возможна: право есть, но действие не видно из-за профиля, personalization, ApplicationArea или настройки функции. [Users and profiles](https://learn.microsoft.com/en-us/dynamics365/business-central/admin-users-profiles-roles).

## 9. Как разбирать отказ

1. Сохраните точный текст: object type, ID, операция, tabledata.
2. Убедитесь в правильной Company и пользователе.
3. Посмотрите Effective Permissions и источник прав.
4. Проверьте direct/indirect и объекты в цепочке вызова.
5. Отдельно проверьте entitlement и environment access.
6. Если права есть, ищите бизнес-проверку, а не продолжайте добавлять permission sets.

Permission recording может помочь обнаружить используемые объекты, но запись одного успешного сценария не доказывает полноту всех рабочих случаев и не заменяет осмысленную минимизацию прав.

## 10. Практика

В учебной среде используйте отдельного тестового пользователя с ограниченными правами:

| Опыт | Что нужно доказать |
|---|---|
| Просмотр Items без изменения | Read работает, Modify запрещён |
| Другая Company | Scope действительно ограничивает доступ |
| Смена Role | UI меняется независимо от permissions |
| Запуск собственной AL-страницы | Есть Execute и нужные права tabledata |
| Проведение документа | Доступ проверяется по полной бизнес-цепочке |

Не считайте проверку под административным пользователем достаточной для выпуска расширения.

## 11. Самопроверка

**SUPER отменяет ограничения лицензии?** Нет.

**Скрытая кнопка защищает данные?** Нет: права и серверные правила нужны отдельно.

**Можно ли создавать пользователей прямо в локальном BC?** Да, в соответствующем on-premises процессе.

**Почему для проведения нужны права на таблицы, которых нет на странице?** Операция работает с несколькими подсистемами, а не только с видимой записью.
