# 2.3. Бизнес-логика, триггеры и транзакции

[Оглавление](README.md) · [События](2.4-al-events.md)

## Уровни выполнения

OnAction относится к действию страницы. Table field OnValidate проверяет изменение поля. OnInsert, OnModify и OnDelete относятся к операциям таблицы при соответствующем RunTrigger. Page triggers обслуживают UI и не вызываются автоматически серверным API или фоновым заданием.

Правило, обязательное для всех входов, должно находиться на серверном пути бизнес-операции. Проверка только в кнопке не защищает от другого вызывающего кода.

## Rec и xRec

Rec представляет текущий буфер, xRec — прежнее состояние в предусмотренном контексте триггера. Сравнение помогает обнаружить изменение, но xRec не является универсальным журналом истории. Для строгой конкурентной проверки иногда нужно повторно читать запись из базы с подходящей блокировкой.

## Error, Message, Confirm

| Вызов | Назначение |
|---|---|
| Error | Прервать выполнение с ошибкой |
| Message | Сообщить пользователю результат |
| Confirm | Получить интерактивное решение |
| TestField | Проверить обязательность или значение поля |

Для background/API кода интерактивный Confirm не подходит. Лучше передавать явный параметр решения из UI в сервис. GuiAllowed помогает отделить доступные UI-эффекты, но не должен молча менять бизнес-правило.

## Граница транзакции

Платформа управляет транзакциями. Если в текущей незавершённой write transaction возникает неперехваченный Error, её изменения откатываются. Ранее зафиксированные транзакции не откатываются.

```text
Insert A → Modify B → Error
Результат: A и B откатываются в пределах одной транзакции.

Insert A → Commit → Modify B → Error
Результат: A остаётся, изменение B откатывается.
```

Commit является архитектурным решением о частичном сохранении. Его нельзя добавлять как универсальное лечение блокировок или ошибок. [Database.Commit](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/methods-auto/database/database-commit-method).

В проекте Item Note Helper.TestRollback вызывает создание заметки и затем Error. Прогноз отсутствия новой заметки верен при отсутствии промежуточного Commit в полном пути вызовов, включая subscribers. Сам текст сообщения «rolled back» не доказывает откат — его проверяют чтением базы после завершения операции.

## Что транзакция базы не откатывает

Отправленное HTTP-сообщение, внешний email и другие внешние эффекты нельзя отменить SQL rollback. Поэтому вызов внешнего сервиса между Insert и Error может оставить удалённый результат без локальной записи.

Для интеграций используют устойчивую очередь исходящих операций: записывают задачу в той же транзакции, затем отправляют после фиксации с обработкой повторов. Подробнее — [интеграции](4.3-advanced-topics.md).

## TryFunction

TryFunction позволяет обработать ошибку через Boolean-результат. Это не автоматическая вложенная транзакция с rollback всех действий внутри.

На on-premises запись внутри try method по умолчанию ограничена серверной настройкой; Online имеет другое поведение. Не проектируйте восстановление данных на предположении, что перехваченная ошибка всегда отменила записи. Также различайте вызов с использованием результата и обычный вызов метода. [Try methods](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-handling-errors-using-try-methods).

Codeunit.Run с Boolean-результатом имеет особую транзакционную семантику. Не подменяйте им обычный вызов публичной procedure, считая их полностью одинаковыми. Проверяйте контракт используемого варианта.

## Конкурентность

Два пользователя могут одновременно прочитать остаток 1 и оба решить, что операция допустима. Проверка, сделанная за секунду до записи без необходимой синхронизации, не защищает инвариант.

Подходы: атомарная операция стандартного приложения, правильный ключ и уникальность, блокировка перед повторным чтением, короткая транзакция, повтор при допустимом конфликте. LockTable не следует воспринимать как простое «навсегда заблокировать всю SQL-таблицу»: поведение зависит от исполнения и изоляции.

Современный tri-state locking отличается от старого поведения NAV; не переносите старые предположения о всех последующих чтениях после записи. [Tri-state locking](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-tri-state-locking).

## Контракт процедуры

Хороший контракт отвечает на вопросы: какие входы допустимы, что изменится, кто владеет Commit, какие ошибки ожидаемы, возможен ли повтор, есть ли внешние эффекты.

Для расчёта ShippingFee желательно чистое возвращаемое значение; сообщение выводит вызывающая страница. Так функцию легко проверить без handlers. В текущем SyntaxPractice.GetShippingFee сообщение вычисляется, но возвращаемый Decimal не устанавливается явно. Это логическая проблема, которую formatter не исправляет.

## Практика

1. Запомните Count заметок конкретного Item.
2. Выполните TestRollback и подтвердите вопрос.
3. После ошибки перечитайте заметки: Count должен остаться прежним при указанном контракте.
4. В отдельном учебном объекте сравните вариант с Commit, не меняя рабочую процедуру.
5. Объясните, почему отправленный внешний запрос не участвовал бы в откате.

**Любая Error откатывает всё за сессию?** Нет, только соответствующую незавершённую транзакцию.

**TryFunction заменяет transaction scope?** Нет.

**Почему Confirm лучше держать до записи?** Чтобы не держать write transaction и блокировки во время ожидания человека.
