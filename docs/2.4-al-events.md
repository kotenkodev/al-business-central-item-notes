# 2.4. События и расширяемость

[Оглавление](README.md) · [Тесты](2.5-al-tests.md)

## Publisher и Subscriber

Publisher объявляет точку расширения. Subscriber выполняет дополнительный код при её вызове. Обычное AL event является синхронным вызовом внутри исполнения, а не очередью и не отдельным фоновым процессом.

| Вид | Назначение |
|---|---|
| Integration Event | Точка расширения прикладной реализации |
| Business Event | Бизнес-уведомление с более устойчивым смысловым контрактом |
| Trigger Event | Событие платформы вокруг операции объекта |

Событие с названием OnAfter… не гарантирует, что транзакция уже зафиксирована. Оно обозначает положение в коде publisher. [Events](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-events-in-al).

## Минимальный пример

Фрагмент publisher внутри собственного Codeunit:

```al
procedure CheckNote(NoteText: Text)
begin
    if NoteText = '' then
        Error('Note text is required.');
    OnAfterCheckNote(NoteText);
end;

[IntegrationEvent(false, false)]
local procedure OnAfterCheckNote(NoteText: Text)
begin
end;
```

Subscriber в другом Codeunit, если publisher назван Training Note Service:

```al
[EventSubscriber(ObjectType::Codeunit, Codeunit::"Training Note Service",
                 'OnAfterCheckNote', '', false, false)]
local procedure RejectReservedText(NoteText: Text)
begin
    if NoteText = 'RESERVED' then
        Error('This note text is reserved.');
end;
```

Это фрагменты для отдельных учебных объектов, а не готовые файлы существующего проекта. Имена события и сигнатуры должны совпасть. Последние параметры управляют пропуском subscriber при отсутствии лицензии или permissions; false не означает «выключить подписку». [Subscribing](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/devenv-subscribing-to-events).

## Как найти правильное событие

1. Определите бизнес-операцию и стандартный объект через отладку.
2. Откройте symbols / доступный исходный код вашей версии.
3. Найдите вызов publisher и прочитайте код до и после него.
4. Проверьте, содержит ли событие нужные данные до записи или после неё.
5. Проверьте var, temporary, RunTrigger и другие параметры.
6. При необходимости используйте Event Recorder на конкретном действии.
7. Протестируйте обычный, ошибочный, повторный и фоновый пути.

Event Recorder показывает вызовы наблюдаемого сценария. Отсутствие события в одном опыте не доказывает, что его нет в другом пути. Название события из чужого примера может отсутствовать в вашей версии.

## var и изменения буфера

Если параметр передан через var, subscriber может менять буфер вызывающего кода. Но это ещё не гарантирует сохранение: publisher может позже заменить значение, повторно прочитать запись или завершиться ошибкой.

Если var отсутствует, изменение локального буфера не меняет переменную publisher. Вызванный Modify постоянной записи всё же изменяет базу — семантика буфера и базы различается.

## Порядок и повторяемость

Не стройте контракт на порядке независимых subscribers. Расширение A не должно требовать, чтобы расширение B обязательно выполнилось первым, если это не организовано явным API.

Повторное открытие страницы, validation, preview posting и повтор операции могут снова вызвать код. Subscriber должен понимать, можно ли создать дубль. Проверка Exists перед Insert без уникального ключа не всегда защищает от одновременного выполнения.

## IsHandled

Распространённый шаблон передаёт Boolean var IsHandled и пропускает стандартную ветку, если subscriber установил true. Это мощное вмешательство: вы принимаете ответственность за заменённые проверки и побочные эффекты.

Несколько расширений могут конфликтовать за этот флаг. Если достаточно дополнить проверку или данные, выбирайте событие с более узким контрактом. Не устанавливайте IsHandled лишь для подавления неудобной ошибки.

## Транзакции и UI

Обычная ошибка subscriber может отменить всю текущую операцию publisher. Commit внутри подписки способен неожиданно разрушить атомарность чужого кода. Не отправляйте внешние сообщения из OnAfter… на предположении, что документ уже окончательно проведён.

Изолированные события имеют отдельные правила и должны рассматриваться по конкретной декларации. Они не превращают любой subscriber в безопасную асинхронную интеграцию.

## Практика и самопроверка

Изучите существующий ItemNoteEvents: определите publisher, момент вызова, параметры и затрагиваемые данные. Поставьте breakpoint и вызовите операцию из UI и Codeunit. Сравните число вызовов.

**OnAfter означает после Commit?** Нет.

**Можно ли рассчитывать на порядок подписчиков?** В общем случае нет.

**Почему subscriber работает при Insert(false)?** Некоторые платформенные события имеют собственные правила вызова и параметр RunTrigger; его нужно проверять по контракту события.
